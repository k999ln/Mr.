# avocadomini 立ち上げ設計書

**Version:** 0.2
**更新日:** 2026-09-04
**運営責任者:** Kai
**状態:** Launch preparation / 実装状態と未接続項目を含む共有用設計書

## 1. 一言で何を作るか

avocadominiは、Telegramを操作画面にして、商品を作る・確かめる・売る・届ける・結果を測るまでを10個のBOTでつなぐ販売自動化基盤である。

> 人間は、やりたいことを。AIは、残り全部を。

ユーザーは最初に3つの道具を無料で選ぶ。外部への投稿、決済、納品、報酬分配などは、必要な設定と承認と実行証拠が揃った場合に限り実行する。

## 2. 誰の何を解決するか

### 最初の対象

- 教材、ツール、有料コミュニティを販売する個人・小規模事業者
- X、Telegram、メール、LP、決済、納品を手作業でつないでいる人
- AIで原稿は作れるが、確認・予約・入金確認・権限付与が人手のままの人

### 解決する問題

1. ツールが分断し、同じ情報を何度も入力する。
2. 投稿が売上・継続・返金にどうつながったか分からない。
3. 決済後の納品、権限付与、失敗回収が漏れる。
4. AIの提案後の実行と確認を人間が肩代わりしている。

## 3. ユーザー体験

```text
公開サイト
  → 「無料スタート」
  → Telegramでavocadominiを開く
  → 解決したい問題に合わせて3つを選ぶ
  → 依頼をひとことで送る
  → BOTが不足条件を整理する
  → 実行計画と承認必要操作を分ける
  → 承認済みの範囲だけ実行する
  → 外部サービスの応答で結果を確認する
  → 成果、未完了、次の一手をTelegramへ返す
```

無料開始時にカードとメールは求めない。現行方針は「3ツールまで無料、4つ目でTelegram Starsの購入確認、成功通知を検証後に10ツール解放」である。

## 4. 10個の道具

| # | 道具 | 役割 | 実行の成果 | 現在地 |
|---:|---|---|---|---|
| 01 | 受付BOT | 依頼の受付 | 不足条件を補い実行可能な依頼にする | 実装済み・未設定 |
| 02 | 教材BOT | 教材作成 | メモ、音声、URLから商品版を作る | 基盤段階 |
| 03 | 確認BOT | 出典確認 | 主張、出典、要修正を対応付ける | 基盤段階 |
| 04 | 販売BOT | LP・オファー | 商品、価格、特典、約束版を固定する | 基盤段階 |
| 05 | X投稿BOT | 投稿作成・予約 | 教材から投稿とツリーを作る | 基盤段階 |
| 06 | 配信BOT | 顧客別配信 | Telegramとメールで届け分ける | 基盤段階 |
| 07 | 決済BOT | 決済・失敗回収 | 入金確認後だけ売上を確定する | 実装済み・未設定 |
| 08 | 納品BOT | 納品・権限付与 | 教材、ツール、コミュニティ権限を開閉する | 実装済み・未設定 |
| 09 | 分析BOT | 施策・売上分析 | 施策を購入・継続・返金へつなぐ | 基盤段階 |
| 10 | 分配BOT | 報酬分配 | 確定成果から取り分と明細を作る | 基盤段階 |

**重要:** 現行の10道具は、ディレクトリ単位のmanifestとregistryで独立管理されている。新しい道具は新規フォルダと`tool.json`で追加し、安全性検査とregistry testを通す。

## 5. システム境界

```text
公開Webサイト
   │  説明・無料開始導線
   ▼
Telegram Bot / Command UI
   │  依頼受付・ツール選択・承認・通知
   ▼
avocadomini Orchestrator
   ├─ Policy: 無料枠、権限、予算、承認
   ├─ Planner: 依存関係、実行順序、不足条件
   ├─ Tool Registry: 道具ごとの権限と実装状態
   └─ Receipt Ledger: 依頼、承認、実行、結果、失敗
   │
   ▼
Provider Adapters
   ├─ Telegram / Telegram Stars
   ├─ X / Email / Landing Page
   ├─ Stripe / LMS / Community
   └─ Calendar / Maps / Browser等の拡張機能
```

外部providerの資格情報がない場合は自動的に停止する。モデル出力やボタンクリックだけを完了とせず、外部応答、message ID、payment event、反映確認などのreceiptを必要とする。

## 6. データ設計

価値があるのは生の会話ログではなく、「誰に・何を・なぜ見せ・何を実行し・どの結果になったか」の閉じた記録である。

### 主要オブジェクト

- Merchant / CustomerAccount / Consent
- Product / ProductVersion / Offer
- ContentAsset / ContentVersion / Claim / Source
- Campaign / Experiment / Exposure / Intervention
- Order / Payment / Subscription / Entitlement
- Outcome / AuditEvent / Receipt

### 必須原則

- 販売者をまたぐ人物追跡IDは作らない。
- 同意目的、同意文面、version、取得元を記録する。
- 匿名集計、モデル学習、第三者提供、買収時承継は別の権利として扱う。
- 外部操作は承認者、理由、実行時刻、結果を一続きで残す。

## 7. 課金設計

### 無料枠

- カード・メール登録なし。
- Telegramで最初の3ツールを選択。
- 同じツールの再選択は二重カウントしない。

### 有料枠

- 4つ目の有効化時にTelegram Starsの決済確認を開く。
- ユーザーの明示操作と`successful_payment`検証後に10ツールを解放する。
- Stars価格、法定表示、返金窓口、test決済・自動解放・返金E2Eの確認完了まで本番課金を有効にしない。
- Stripe導線は互換用であり、新規ユーザーの既定入口にしない。

## 8. 現在の実装判定

### 確認済み

- 公開マーケティングサイト。
- 10道具の個別manifest、registry、追加時の安全性test。
- Telegramの無料3ツール選択、4つ目の制限、Stars invoice生成、成功通知からの権限更新のコード。
- 依頼から選択ツールへ展開する計画生成と、無料上限違反の停止。

### 本番前に接続・確認が必要

- Kai所有のTelegram Bot username / token / webhook secret / 公開HTTPS origin。
- Telegram Starsの実価格と本番有効化。
- 法定表示、privacy、返金対応、問い合わせ先。
- 10道具の実executor、provider credential、外部反映のreadback。
- テナント分離、保存期間、削除、export、障害時の停止と復旧。
- X・メールなどの外部送信は、所有アカウントと承認フローを確認する。

## 9. 立ち上げフェーズ

### Phase 0 - 売らないクローズドテスト

- Kaiと共同開発者のみ。
- Telegram接続、無料3ツール、権限停止、receiptを検証。
- 実際の課金・自動投稿・自動送金は無効。

### Phase 1 - 10人の無料パイロット

- 受付BOTと外部操作のないツールを中心に検証。
- 初回価値到達時間、中断率、人間介入率、エラー再実行率を測る。
- 各ユーザーの解決したい問題と選択3ツールの一致を確認。

### Phase 2 - 有料パイロット

- Starsの購入、解放、二重決済防止、返金をE2E検証後に少人数で開始。
- 開発者への報酬はまず明細計算だけに留め、実送金は照合・異議申立・返金時調整が完成してから有効化する。

### Phase 3 - 一般公開

- 指標と事故対応が基準を満たした場合のみ人数を拡大。
- 新規ツールは個別フォルダ、maintainer、capability、承認条件、receiptを必須とする。

## 10. 責任分担

### Kai - Product Owner

- 対象顧客、価格、約束する成果、公開文言の最終判断。
- 公開アカウント、決済受取先、問い合わせ窓口の所有確認。
- 取り消せない操作と予算超過の承認。

### Tool Maintainer

- 自分の道具のmanifest、executor、test、runbook、エラー分類を所有。
- 別ツールのcredentialやテナントデータへ直接アクセスしない。
- 成功判定にreceiptを必須とする。

### Operations / Support

- 障害、返金、データ削除、provider失敗を受付け、状態を記録する。
- 結果不明の操作を完了扱いしない。

## 11. Go / No-Go ゲート

### 無料パイロット開始条件

- [ ] Kai所有のTelegram Botと公開Webhookを検証した
- [ ] 新規ユーザーがサイトから3ツール選択まで到達できる
- [ ] 4つ目が無料で有効化されない
- [ ] 投稿・送信・決済・納品の未承認実行がない
- [ ] 同じupdate・注文・ジョブを二重実行しない
- [ ] 削除依頼、問い合わせ、緊急停止の窓口がある

### 有料開始条件

- [ ] Stars価格と表示を確定した
- [ ] 購入・権限解放・二重決済防止・返金のE2E証拠がある
- [ ] 法定表示、privacy、利用条件、返金窓口が公開されている
- [ ] 購入前に金額と対象を表示する
- [ ] 決済成功通知の検証前に有料権限を開けない

### 自動投稿・自動分配開始条件

- [ ] 所有アカウント、送信対象、承認者、予算上限を固定した
- [ ] provider画面のreadbackで反映を確認できる
- [ ] 返金・異議申立・取消し時の再計算ができる
- [ ] 結果不明時は再送・再送金せず停止する

## 12. 立ち上げ後の指標

| 指標 | 目的 | 初期の判定 |
|---|---|---|
| 無料開始完了率 | 導線の分かりやすさ | 中断箇所を特定する |
| 3ツール選択完了率 | 問題と道具の一致 | 選択理由を確認する |
| 初回価値到達時間 | 価値が出る速さ | 最初の有用な成果までを測る |
| 人間介入率 | 「完全自動」への距離 | 介入理由を機能別に分ける |
| receipt確認率 | 実行の信頼性 | 結果不明を成功にしない |
| 返金・苦情率 | 約束と納品の一致 | 内容とプロセスに分解する |
