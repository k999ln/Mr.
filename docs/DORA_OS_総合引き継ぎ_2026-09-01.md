## 0. 先に読む結論

avocadominiは、当初の「データを蓄積して将来買収される事業」という検討から始まり、Telegramを操作画面にして、コンテンツ作成、投稿、決済、納品、権限、継続、返金、成果検証までをつなぐ販売OSへ具体化した。

現在は次の3段階が混在している。

| 項目 | 現在の状態 |
|---|---|
| 商品説明・事業構想・公開サイト・PDF | 公開済み |
| 販売OSの台帳、承認、Webhook、決済、権限、Telegram Stars等のコード | 実装・テスト済み |
| 一般顧客が実際に購入し、Telegramへ接続し、商品を受け取る本番E2E | **未完了** |

したがって、今すぐできるのは「事業内容、先行案内、PDFを公開して反応を集めること」である。現状を「購入後すぐ全機能が使える正式販売」として告知するのはまだ早い。

本番販売を止めている主な理由は、公開Core、DB migration、Stripe Webhook、Telegram Bot、法定表示、メール配信などの本番設定がつながっておらず、購入から権限付与・返金取消までの実取引receiptがまだないためである。

## 1. この作業で作った事業

### 1.1 現在の一文定義

> avocadominiは、複数のAI・BOT・サービスを一つの目的で動かし、依頼、承認、実行、外部確認、改善までを0から100で完了する実行OSである。

第一段階は、教材、情報商材、有料コミュニティ、デジタルツールを販売する少人数事業者向けの販売OSである。操作画面はTelegramを中心にし、利用者が個別のAIやツールを意識せず、目的を伝えるだけで必要な処理を順番に動かす。

最終構想は販売BOTではなく、家計、サブスク、食事、買い物、家庭用品、育児、学校、予定、地域活動、スマートホームを同じ承認・実行基盤で扱う生活OSである。

### 1.2 一番押す価値

従来の「自動化」は、AIが下書きを作った後に人間が修正し、コピーし、別サービスへ入力し、結果を確認していた。人間がAIの作業員になり、本当に任せたい面倒な処理を人間が担当していた。

avocadominiが押す価値は、生成AIの多機能さではない。

- 初回に目的、予算、好み、禁止事項、承認条件を決める
- 条件内ではAI・BOTが自動実行する
- 高額、健康、安全、子ども、不可逆操作だけ人へ確認する
- 外部サービスの公式記録で成功を確認する
- 結果不明なら勝手に再実行しない
- 失敗しても途中から回復する

つまり「AIを使える」ではなく、「人が触らなくても最後まで完了し、それを証明できる」が中心価値である。

## 2. 検討の変遷と、なぜ現在の形になったか

### 2.1 重要インフラ版Palantirの検討

最初は、データセンターや重要インフラの運用データを統合し、障害の影響予測、復旧順序、承認、実行、事後検証まで扱う「重要インフラ版Palantir」を検討した。

比較した資産は次のとおり。

- 生の設備・センサーデータ
- 匿名化・集計された故障パターン
- 設備、電力、水、通信、供給会社を結ぶ依存関係グラフ
- 障害から復旧までの判断・対応・結果
- 顧客業務を表すオントロジー
- 政府・防衛環境へ導入できる技術、認証、契約実績
- 複数組織をまたぐ復旧ワークフロー

重要な発見は、「顧客固有の依存関係グラフ」と「汎用オントロジー」は別物だという点である。

- 顧客固有グラフ: 顧客の機密資産で、横断再利用しにくい
- 汎用オントロジー: 設備、障害、依存、承認、復旧、結果の共通構造で、自社IPにしやすい
- 匿名集計された故障・復旧パターン: 契約上の再利用権が取れれば蓄積資産になる

ただし重要インフラは、データ持ち出し制限、長い導入期間、重大障害の少なさ、個別SI化、防衛調達の壁が大きい。初期市場としては重すぎる可能性があるため、すぐ5億円を投じる案には進まなかった。

この段階の安全境界として、個人の位置追跡、Wi-Fiによる人物特定、標的選定、兵器、暗殺用途は明示的に対象外とした。

### 2.2 Pokémon GO / Palantir型データ事業の再整理

「無料・便利なサービスを入口にデータを蓄積し、将来より大きな顧客へ売る」という発想も検討した。ただし、価値があるのは秘密裏に生データを転売することではない。

Pokémon GOについても、「生の位置情報を直接軍へ売った」と断定するより、利用者参加型の現実世界データで空間モデルを育て、防衛隣接領域にも接続可能な技術資産を作った、と捉える方が正確である。

事業上の教訓は次の3点だった。

1. 継続的にデータが生まれる業務フローを持つ
2. データ、派生統計、モデル利用、買収時承継の権利を先に取る
3. 生データではなく、共通構造、判断、実行、結果の閉ループを資産化する

### 2.3 Telegram販売OSへの転換

重要インフラより早く事例と成果ラベルを得られ、顧客の損失と価値を測りやすい市場として、教材、ツール、有料コミュニティの販売業務へ転換した。

Telegramは投稿先ではなく、販売者がAI・BOT・決済・会員管理を操作する司令塔として位置付けた。

この転換で、重要インフラ検討で得た次の考え方を商取引へ移植した。

- 依存関係グラフ → 商品、オファー、投稿、決済、権限、顧客成果の関係
- 復旧ワークフロー → 決済失敗、納品漏れ、返金後権限残存の検知と回復
- オントロジー → 販売者をまたいで使える共通商取引モデル
- 監査証跡 → 誰が、なぜ、何を承認・実行したか
- 外部確認 → Stripe、Telegram等のreadbackがある時だけ完了扱い

## 3. avocadominiの10機能

現在の説明上の10機能は次のとおり。

1. **コンテンツ作成** — 教材、記事、X投稿、Telegram投稿、メルマガ、LP文面
2. **ファクトチェック** — 主張、出典、確認が必要な箇所を整理
3. **投稿管理** — 媒体別変換、投稿プール、承認、予約配信
4. **オファー作成** — 商品、価格、特典、期限、対象者、成果条件
5. **承認管理** — 予算、価格変更、公開投稿など重大操作の承認
6. **BOT連携** — MCP、API、Webhook、必要最小限のRPA
7. **決済** — Stripe / Telegram Stars、支払い結果の確認
8. **納品・権限付与** — 教材、ツール、コミュニティ権限の付与
9. **継続・失敗回収** — 更新、解約、返金、決済失敗、権限停止
10. **売上検証** — 投稿、価格、特典と購入、継続、返金の関係

重要なのは、10個を別々の便利ツールとして見せないこと。一つの依頼を完成させる連続した能力として見せる。

初期の最重要ユースケースは次である。

> 決済した人へ商品を自動で届ける。決済失敗を回収する。返金・解約後は権限を止める。

ここが最も外部結果を確認しやすく、顧客へROIを説明しやすい。

## 4. データ設計と将来の買収資産

### 4.1 価値が低い、または危険なデータ

- 生のTelegram会話
- メールアドレス一覧
- 投稿本文だけ
- フォロワー数やクリック数だけ
- 同意のない人物横断ID
- 秘密値、token、password

これらは模倣可能で、権利・プライバシー負債になりやすい。

### 4.2 価値を持つ閉ループ

価値の中心は次の連鎖である。

```text
顧客状態
  → 商品・オファー・訴求
  → 選定理由・承認
  → 配信・実行
  → 購入・納品・利用
  → 継続・返金・解約
  → 純経済価値と改善結果
```

共通オントロジーでは、Merchant、Product、Offer、ContentAsset、Claim、Source、Campaign、CustomerAccount、Consent、Touchpoint、Intervention、Order、Subscription、Entitlement、Outcome、Experiment、AuditEventを扱う。

特に切断してはいけない関係は次である。

```text
ContentAsset → Campaign → Offer → Approval → Intervention
→ Payment → Entitlement → Outcome
```

### 4.3 必要な計測工程

- 全オブジェクトへmerchant-scoped IDを付ける
- 投稿、LP、価格、教材、約束のversionを固定する
- 誰に何をいつ見せたかを記録する
- UTM、専用URL、ディープリンク、クーポンで経路をつなぐ
- 施策を選んだ理由と承認者を記録する
- テスト群・対照群・選択確率を持つ
- 購入だけでなく返金、解約、継続、苦情まで追う
- Webhook欠損、重複、遅延、署名不正を検知する
- 不明、保留、失敗、未購入を区別する

### 4.4 権利境界

販売者をまたぐ人物追跡IDは作らない。顧客IDは販売者ごとに分離し、横断分析は許諾済みの匿名集計に限定する。

契約・同意は少なくとも次を分ける必要がある。

- サービス提供
- 販売者自身の分析
- avocadominiの製品改善
- 匿名集計ベンチマーク
- モデル学習・評価
- 第三者向け集計商品の提供
- 契約終了後の派生統計保持
- 買収時の権利承継

これらを取れなければ、データ企業ではなく個別SI・受託へ戻る可能性が高い。

## 5. 実装した販売OS基盤

### 5.1 商取引の正本

実装ではStripeやTelegramを正本にせず、avocadomini内のcanonical recordsを中心にした。

- immutableな商品、Offer Version、Promise Version
- providerから観測したPayment、Refund、Chargeback
- Entitlementのdesired state / observed state
- Consent、Rights、Purpose、Notice Version、Withdrawal
- Approval principal、authorization policy
- Decision Opportunity、候補、却下、選択確率、model / policy version
- 実行、readback、Outcome、純経済価値
- 不一致とReconciliation Case

Stripe、Telegram、Stars、LMS、Community、License、CMS、CRM、実験基盤は交換可能なadapterとする。

### 5.2 実装上の安全性

- `merchant_id`をID、query、idempotency、authorization境界へ含める
- Telegramの実actorが取れない場合、架空の所有者へfallbackしない
- 同じWebhookを再送しても効果を一度にする
- 別tenantで同じjob/effect IDが衝突しない
- 遅延決済成功にも対応する
- 決済成功・権限未付与、返金済み・権限残存を不一致として検出する
- provider readbackなしに完了・売上を確定しない
- 未確定結果を勝手に再送せず停止する

### 5.3 主要モジュール

- `commerce-assurance-store.js` — 商品、約束、決済観測、監査の正本
- `commerce-webhook-inbox.js` — merchant-scoped Webhook inbox、署名、再送、衝突
- `commerce-purchaser-entitlement-store.js` — 購入者のdesired / observed権限
- `commerce-consent-rights-store.js` — 目的別同意、権利、撤回、抑止
- `commerce-decision-store.js` — 候補、確率、holdout、policy/model、結果
- `commerce-event-ledger.js` — イベント台帳
- `commerce-workflow-*` — ワークフロー計画、実行、永続化、回復
- `doraemon-purchase.js` — Stripe購入claimとTelegram接続
- `doraemon-stars.js` — Telegram Stars商品販売

### 5.4 Telegram Stars

Telegram内でデジタル商品を販売するため、Stars対応を追加した。

- `/buy`
- `/terms`
- `/support`
- `/paysupport`
- 同意callback `dora:agree`
- XTR invoice
- pre-checkout検証
- 支払い後grant
- refund後revoke
- Telegram payment charge IDの保存

StripeとStarsは販売チャネルが違うため、同じ顧客claim・権限台帳へ観測を入れる構成にした。

### 5.5 OSS候補

次のOSSを固定commitのsubmoduleとして評価用に追加した。

- Formance Ledger
- Temporal
- OpenFGA
- grammY
- Payload
- GrowthBook
- Casdoor
- Chatwoot
- Medusa

これらは**現在の本番依存ではない**。採用前にlicense、security advisory、tenant isolation、telemetry、backup、export、削除、差し替え手順を確認する。

## 6. 公開サイトとデザイン

### 6.1 作ったもの

公開サイトには次を実装した。

- avocadominiの説明
- 10機能のストーリー表示
- 商品説明、価格、購入導線
- Telegram接続の説明
- 無料診断PDFのメール取得LP
- UTM、同意、任意属性の保存
- Turnstileのserver-side検証
- Resend即時送付と予約メール
- unsubscribe
- privacy / legalページ
- GSAPによるスクロール・カードアニメーション
- iPhone向けレスポンシブ表示

### 6.2 デザインの変遷

初期版は、黒背景、細い枠、`BOT → DATA`の線図が10枚続く構成だった。以下の問題があった。

- 10個の別機能ではなく、同じ図の繰り返しに見える
- BOTが何をしているか直感的に分からない
- Apple的な製品体験より技術説明資料に見える
- 購入ボタンが右上だけで見つけにくい
- スクロール中の購入導線が弱い

そのため、GSAP、Apple Design系の設計原則、mono-colorを参考に、余白、明暗、pill CTA、独自図解、sticky CTA、個別機能ごとのモーションへ寄せた。

Apple、Stripe等のデザイン分析repoは公式ブランドライセンスではない。Appleのロゴ、写真、SF Proの再配布、固有コピー、公式に見える表現は避け、抽象的な設計原則だけを利用する方針にした。

### 6.3 現在の公開状態

- 公開URLはChatGPTアカウントなしで閲覧可能
- PDFも直接URLからPC・iPhoneで開ける
- 公開サイトの購入ボタンは、本番Coreが設定されていないため意図的に「Stripe決済を準備中」にしている

これは表示バグではなく、決済だけ成功して納品できない事故を防ぐfail-closedである。

### 7.2 Telegram

既定はBYOB single-botである。各設置者がBotFatherで作ったBotを、1 deployment = 1 Botとして接続する。

まだ必要なもの:

- Kai所有のTelegram Bot username
- Bot tokenをCoreのSecret Storeへ登録
- webhook secret
- 公開HTTPS Core URL
- `setWebhook`後のreadback
- 本人Telegramで`/start`、購入claim、権限付与を確認

tokenやwebhook secretはチャット、Git、公開HTMLへ入れない。

### 7.3 Railway

公開Coreの候補としてRailwayを開き、GitHub OAuthを進めた。しかし表示されたGitHubアカウントは`noellesugar99`で、所有者SSOTの`k999ln`と一致しなかったため停止した。

再開時は、Railwayで`k999ln`のGitHubへ切り替え、対象repoへの権限を確認してからdeployする。所有者不一致のまま承認しない。

### 7.4 本番販売までに必要なE2E

```text
サイト購入CTA
  → Stripe live Checkout / Payment Link
  → 署名済みWebhook
  → avocadomini Coreの購入観測
  → 一度限りのpurchase claim
  → Telegram本人接続
  → 商品・権限付与
  → provider readback
  → 返金
  → 権限取消
  → 全receipt保存
```

この一周を実アカウントで通し、二重Webhook、遅延決済、返金、結果不明も確認してから正式販売を開始する。

## 10. 特許構想

Amazonの1-Click特許を参考に、「保存済みの運転ポリシーを一度の操作で起動し、複数BOTを連携させ、外部成果を検証し、抽出された報酬をBOT製作者へ分配する仕組み」を検討した。

単なる「ワンクリック自動化」は特許として弱い。候補になるのは、次の技術的組み合わせである。

- 保存済み運転ポリシーによる自律処理
- 操作リスクに応じた自動実行・承認切替
- 一度だけ実行するidempotency
- 外部サービスreadbackによる成功確認
- 結果不明時に再送せず停止する制御
- 複数BOTを共通成果へつなぐオーケストレーション
- 外部成果に紐づく利用料確定と製作者分配

既に`patent-strategy.pdf`はサイトのpublic assetsにあるが、これは出願済み特許ではない。出願前に先行技術調査と弁理士確認が必要で、公開済み内容が新規性へ与える影響も確認する。

## 12. 途中で起きた課題と学び

### 12.1 別プロジェクトとの混線

途中でPRIVATE / PIXELやGrapheneOSの話が混ざった。avocadominiは10個の販売ツールとTelegram連携のプロジェクトであり、Pixel端末インストーラーとは別である。

現在もworktreeには未追跡の`apps/private-pixel-installer/`と`apps/private-pixel-site/`がある。avocadomini作業では触らない。

### 12.2 名前と権利

「ドラえもん」は著名な第三者キャラクター・商標と衝突する可能性がある。公開ブランドは独自名称`avocadomini`へ寄せたが、Sitesのタイトル、古いファイル名、本文には「ドラえもん」が残っている。

正式販売前に、表示名、商品名、Bot名、X名、明細書表記を`avocadomini`または別の独自名称へ統一する。

### 12.3 公開と販売の混同

サイトが公開されていること、Stripeリンクが存在すること、コードがテスト済みであることは、「顧客が購入後すぐ利用できる」ことを意味しない。

今後は次の3つを必ず分ける。

- `public`: 説明ページを誰でも見られる
- `payment-enabled`: 本番決済が成功する
- `fulfilled`: 購入後の接続、納品、権限、返金取消まで完了する

### 12.4 UIの説明不足

初期の10枚の`BOT → DATA`図は、機能差が分からず、同じカードの繰り返しに見えた。機能名を並べるだけではなく、「通知が届く」「権利を確認する」「決済を確認する」「商品を届ける」など、入力、BOTの動作、受け手、結果を各シーン固有のアニメーションで示す必要がある。

### 12.5 購入CTA

右上だけの購入ボタンは見つけにくかった。sticky bottom CTA、中間CTA、価格直後CTAを入れる方向に変更した。ただしCore未設定時は購入ボタンを無効にし、準備中と明示する。

### 12.6 所有者アカウント

GitHubのSSOTは`k999ln`。Railway OAuthで別アカウントが出たため停止した。外部公開、決済、Bot、SNS、メールは、Kai所有の接続先を確認できない限り進めない。
